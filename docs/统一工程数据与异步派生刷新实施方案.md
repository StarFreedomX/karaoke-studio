### 1.2 历史排查证据与待解决问题

- 原始独立面板采样中，30 次字号修改触发 240 次字重下拉刷新、2160 次字重解析，总计约 74ms。该数字是修复前的局部探针，不代表真实工程卡顿总耗时，也不能直接作为最终版本收益。
- 曾验证同字体族缓存未包含字体代际、layout scope 被过滤；这两项已纳入批次 1，不能重复当作当前未修复缺陷。
- 预览派发前的 `engine/text/font_preparation.py::prepare_fonts` 包含字体收集、样式转换和逐轨逐字符的回退准备。缓存命中不一定消除外层遍历；这是松手后 UI 同步耗时的重点测量链路。
- `native/backend.py::_send` 等待发送锁并写入、flush 管道。请求侧不等响应并不保证发送非阻塞；阻塞风险须按 P2 验证和处理。
- 轨道窗口及诊断等后台路径应检查是否仍以浅拷贝列表共享可变轨道、读取实时窗口状态，以及 generation 是否在编辑时立即失效；按功能迁移补齐，不以批次 1 的完成推定全局异步安全已解决。
- 歌词列表已有签名判重和列级刷新，轨道绘制已有视口裁剪；这些不等于计算、数据投影也已按可见范围减负。
- 撤销合并仍应核查是否每次完整序列化前后样式；偏好保存的防抖不等于后台写入。二者按真实同步耗时进入 P1/P4。

## 2. 数据所有权：复用已有 Document

现有 `project/session.py::SubtitleProjectDocument` 已保存 style、主轨、副轨、素材等工程内容，并有轨道修改接口；`contracts.py::SubtitleProjectState` 是对宿主发布的状态摘要，不是完整渲染快照。

以现有 Document 为唯一工程事实来源，在其周围增加轻量提交协调器（下文暂称 ProjectStore）。不要再复制一份可写的 style/tracks 到新 Store。UI 中兼容的 `_style`、`_timing_track` 等只能是访问适配或只读投影。

| 层 | 内容 | 所有者与规则 |
|---|---|---|
| 工程事实 | 歌词、时间、角色、字体、布局参数、素材引用 | Document；统一命令提交，立即更新 |
| 派生状态 | 分页、字形几何、显示窗口、诊断、渲染资源 | 计算服务；固定输入、版本化结果 |
| UI 状态 | 选中、滚动、当前页、展开、未提交输入文本 | 对应视图；不得成为渲染事实来源 |

“后台数据”指独立数据层，不要求权威模型移到后台线程。轻量提交仍在 UI 线程完成，耗时计算异步执行。渲染、保存与导出不读取控件值作为已提交工程状态。

## 3. 提交协议与事务

拟议接口：`dispatch(command) -> ChangeSet`、`snapshot(requirements) -> ProjectSnapshot`。事件发布可由 Qt 适配器完成，数据层保持无 QWidget 依赖。

命令包括设置样式字段、角色字段、布局字段、逐行动画、时间覆盖、替换字幕源等。命令目标使用稳定对象标识；迁移初期可用“会话标识＋轨道结构版本＋索引”，但不能把裸行号跨结构修改复用。

提交顺序：校验和归一化 → 准备所有关联变化 → 原子替换 Document 内容 → 记录撤销 → 更新版本/标脏 → 发布 ChangeSet → 调度派生计算。回填控件不再次生成命令。

ChangeSet 至少包含：

```text
session_id, revision, previous_revision
changed_paths, affected_track_ids, affected_line_ids, affected_layout_ids
impact = {font_resources, geometry, display_timing, paint,
          list_presentation, timeline_cells, app_preferences}
full_invalidation
```

- 角色重命名及引用重映射、布局缩容及重分页必须作为同一事务，异常时不留下半份修改。
- 既有 `mutate_track/mutate_tracks` 使用原地修改及快照；迁移时改为在候选副本操作、成功后交换，或提供经过验证的回滚。不能因接口名称有 atomic 就假定异常时已经原子化。
- 文本框允许保留未提交文本；保存/导出等命令先按统一编辑提交策略处理活动编辑器，然后取得最新快照。
- 纯同值命令不增加版本、不入撤销栈、不调度任务。
- 重量级编辑命令若需后台准备，先基于固定版本计算候选结果，UI 验证基线后一次提交；发生冲突时重算或明确解决，不能无条件覆盖期间编辑。

## 4. 快照与版本

### 4.1 稳定输入

后台不得共享 UI 正在原地修改的 TimingTrack、TimingLine、嵌套 Style 列表/字典。`list(tracks)`、浅层 `replace(style)`、外壳 frozen dataclass 均不等于深层不可变。

第一阶段按内容版本缓存专用计算快照，只在内容修改时重建受影响轨道；纯字号修改复用内容快照。已发布的快照永不原地修改。后续逐步采用不可变节点和局部替换，避免每次输入深拷贝整首歌。

字体、图片等外部资源还需要资源代际。工程保存的是资源引用；计算结果必须注明使用的资源版本，不能仅以路径字符串判定资源未变化。

### 4.2 版本分工

- session_id：新建、打开、切换工程时变化，隔离跨工程结果。
- revision：每次成功编辑单调递增；撤销也是新 revision，不退回旧编号。
- dependency token：内容/结构、几何、绘制、显示时间、字体代际、画布等相关版本组合。
- request_id：唯一任务编号，用于完成通知、busy 与取消管理。
- view_epoch：当前可见范围或跳转需求；决定投影位置和优先级，不修改工程事实。

首阶段可保守按全 revision 验收。后续允许不受本次编辑影响的结果复用，但须以完整依赖 token 证明相容，不能仅凭“都是同一字体”或单一 scope。

编辑提交时立即更新版本并失效；防抖只延后启动计算。不能等计时器触发才令旧结果失效。

## 5. 统一派生状态与调度

拟议 `DerivedStateStore` 保存版本化布局计划、轨道投影、诊断和资源准备状态；不保存第二套可编辑工程事实。优先复用现有 `engine/layout/plan`、显示解析和缓存接口。

```text
ComputeRequest = session + request_id + dependency_token
                 + stable_snapshot + requested_range + cancel_token
ComputeResult  = 原请求身份 + completed_range + immutable_payload
                 + coverage_status + error
```

调度优先级：当前画面/跳转目标 → 可见轨道 → 即将播放范围 → 全工程诊断和远处预取。相同依赖的计算共享一个任务；队列有界，连续输入合并尚未开始的旧请求。

发布规则：

1. 核对会话、依赖、资源代际和所需覆盖范围。
2. 过期结果不发布；如保留缓存，也只能挂在原 token 下并受容量限制。
3. 视口已变化但数据仍有效时，可进缓存，不能覆盖新视口请求状态。
4. busy 按 request_id 管理，旧任务结束不清除新任务 busy。
5. 需要配套使用的几何、窗口和绘制参数作为相容结果组合发布，禁止新字号套旧坐标。
6. 计算失败保留错误/待更新状态，不能将旧结果重新标记为当前版本。

后台不读取 `self._extra_sources`、窗口控件或实时 `_style`。诊断函数应接收来源名称、轨道快照、画布和配置；缓存归服务所有。共享缓存需明确线程所有权或锁保护，锁内不做布局、字体查询、信号回调或 I/O。

## 6. UI 和渲染如何消费

### 6.1 属性面板和歌词列表

属性面板从 Document 投影当前对象；按 ChangeSet 更新相关控件组，隐藏页记录脏版本，显示时补齐。值已提交就与控件是否刷新无关。

歌词普通文字、角色名称直接读取 Document；依赖布局的内容读取相容派生结果。将列级刷新函数改为接受行集合，维护每行/列的待刷新版本，滚动、切源、窗口变化时刷新可见行及预取行。

复制、批量编辑、保存和导出必须读取模型。需要审计所有 `item.text()` 等读取：若用于业务操作，改为模型查询；若仅用于展示测量可保留。分组行更新扩展至整个组合；隐藏视图不应因 rowAt 无效而回退刷新全表。

### 6.2 轨道

将普通字符块、Utopia 视觉字符块、显示窗口三个依赖分开。普通块按行内容版本缓存；Utopia 块依赖真实几何/ruby/时间参数，配色不引起重建。显示窗口由共同布局计划投影。

维护完整轻量时间索引，支持总时长、缩放、跳转和命中测试；详细行块按相交区间查询。选中行即使不在视口也属于优先范围。显示窗口未就绪时不允许用过期把手坐标提交拖动；可暂时禁用把手并优先准备该行。

### 6.3 预览和未显示区域

所有受影响区域立即失效，可见范围只决定计算优先级。播放、滚动、跳转均会请求所需版本；播放前预取不代替任意跳转的正确性检查。

第一阶段保留完整布局计算，仅复用结果、缩小 UI 投影和已证明安全的绘制更新范围。后续才将布局分为全局轻量索引与页/段结果。

局部布局必须计算完整依赖闭包：同页对齐、SmartHorizon、页间避碰、同步入退场、段首段尾、间奏填充、标题与活动动画；相邻结果受影响时继续扩展到稳定边界，无法证明独立时回退整段/整轨。不能固定取前后各一页便宣称正确。

GPU 补丁注明基线与目标版本，并包含删除项；sidecar 基线不匹配或重启时重新配置完整场景。不能把基于 A 的增量补丁应用到 C。

新画面未准备好时进入明确的 pending 状态，优先请求计算。可以选择暂留上一完整预览并显示“正在更新”，但不得把它标成当前版本或用于导出；播放位置已改变时避免把旧时刻字幕继续叠在新视频上，应明确清除字幕层/等待新层。具体展示策略统一处理，不能由各 worker 随意决定。

## 7. 执行线程边界

| 工作 | 执行位置 |
|---|---|
| 轻量命令提交、撤销提交、版本更新 | UI 线程，单写者 |
| QWidget、QPixmap 和单元格更新 | UI 线程 |
| 当前字体契约要求的 Qt 字体查询/缺字准备 | UI 线程，缓存＋小时间片分批 |
| 布局、诊断、显示窗口计算 | 后台，稳定输入 |
| 栅格渲染 | 既有 worker/sidecar |
| sidecar stdin 发送 | 专用串行发送器 |
| 工程及偏好文件 I/O | 串行保存服务 |

`engine/text/font_preparation.py` 先按内容/角色/字体版本缓存字符集合，仅处理新增资源。保持项目已有 Qt 字体线程契约，不把整段 prepare_fonts 简单移至线程。准备好的资源快照要固定代际；后台缺资源则请求准备，不能悄悄回到危险的 Qt 查询路径。

`preview_async.py` 的 UI 请求侧只更新有界请求槽和取消标记。`native/backend.py` 管道写入/flush 由发送器处理，避免 UI 持 condition 锁等待 send_lock。消息携带 sidecar 实例标识，保证配置、取消和差分补丁顺序；旧进程消息不得投递到新进程。堵塞恢复及进程退出不阻塞 UI，不能新增多个 stdin 写入者。

## 8. 保存、导出与撤销

- 工程保存取得最新已提交快照，不等待 UI 刷新或预览完成。保存成功只确认对应 revision；期间的新修改继续保持 dirty。
- 导出取得固定完整快照，独立确保全部资源与布局就绪。后续编辑不改变正在导出的内容。外部素材发生替换时应检测并明确处理，不得混用资源版本。
- 撤销与重做经过相同命令/事务通道，产生新版本和失效集合；旧帧无法恢复被撤销效果。
- 常规样式撤销保存字段差异；关联轨道结构修改保留完整事务信息。不存在第二套独立撤销栈。
- 偏好与工程内容分开，仅偏好真的改变时保存。现有 `settings.py` 固定 `.tmp` 和读改写语义要求所有同文件写入口串行化；如支持多实例，还需进程间协调及冲突合并，进程内队列不足以保证多实例安全。
- 保留未知字段、预设合并与宿主 provider 契约。未声明线程安全的 provider 不能直接放进后台调用。
- 关闭时禁止新请求，失效所有 UI 结果回调，停止计算并完成保存收尾；保存失败显式处理。任务不得在窗口销毁后访问 Qt 对象。

## 9. 用户体验优先的交付顺序

完整数据架构用于约束方向，不作为所有小优化的打包前置。每个批次应能独立验证和发布；一个批次内也可按下列子项分别交付。具体优先级可按真实工程采样调整，未经测量不承诺固定提速倍数。

| 批次 | 用户直接感受到的改善 | 最小交付范围 | 正确性前置与边界 |
|---|---|---|---|
| P0 | 调字号、字体和配色时面板更轻快 | 已完成的批次 1，收尾验证后独立 release | 依第 13 节；不等其他批次 |
| P1 | 松手后不因一批刷新任务集中执行而卡住 | 优先削减预览派发前字体扫描/序列化、轨道投影、歌词列刷新、偏好准备等同步工作；字体小样判重、角色扫描按依赖跳过 | 缓存键覆盖真实依赖及字体代际；不改变渲染范围，不新增线程共享状态 |
| P2 | 松手后后台仍在更新时，可以立即继续点击、滚动和编辑 | P2a 字体准备仅处理新增资源并按 UI 时间预算分批；P2b sidecar 发送离开 UI；P2c 控制后台 CPU 并发、诊断空闲执行、结果投影分批 | 每个异步子项自带稳定输入、版本立即失效、结果验收及生命周期；允许首帧稍晚，完整布局继续保留 |
| P3 | 长歌词列表滚动、切特效和轨道缩放更流畅 | P3a 相同单元格不重复赋值、受影响列刷新；P3b 模型驱动的可见行刷新；P3c 轨道区间索引和行块缓存 | P3a 可先独立发；P3b 必须审计复制/编辑读取，不得依赖旧单元格；P3c 保留完整时间索引和正确把手数据 |
| P4 | 大工程调参、停手保存时不再出现额外顿挫 | 撤销字段差异、只保存真正变化的偏好；需要时引入串行保存服务；共享完整布局结果 | 先减量再异步；涉及保存线程时统一同文件写入口与版本确认 |
| P5 | 超长、多轨工程重排等待进一步缩短 | 在已验证的共同布局结果上做页/段增量、播放预取、局部 GPU 更新 | 完整依赖闭包、补丁基线校验和完整算法差分；最后实施 |

### P1 的具体落点

- 首先测量停止输入后 0–3 秒的 UI 事件延迟，逐项标记轨道刷新（当前约 120ms）、预览/列表刷新（约 150ms）、诊断（约 400ms）、偏好保存（约 1500ms）的实际同步耗时；以代码最终配置为准。这些定时器晚执行，不代表其中的工作异步。
- 优先处理 `_apply_preview_style_now → prepare_fonts`、轨道 `set_style` 的重建、歌词列更新和偏好保存准备。对每条链分别计时，不以后台 render 耗时代表 UI 阻塞时间。

- `main_window.py::_apply_style` 不再无条件重新收集全部角色。缓存 `_merged_role_options` 的输入，只在角色注册表、歌词角色内容、标题角色引用或来源结构变更时更新；字体/字号/配色不触发。
- 字体小样缓存实际生效样式签名，宿主回流相同状态不重新请求；保留字体代际失效。
- `font_preparation.py` 先实现保守快速路径：纯配色变化、内容/角色/字体资源未变时复用准备结果。字号是否可以跳过应按资源准备的实际依赖判断，不能以“字形相同”猜测。
- 不引入新的漏失效风险：无法证明缓存键覆盖所有输入时，继续走原路径。暂不做逐页字体裁剪和局部布局。

### P2 的最小架构投入

不先改写全部 Document/命令/撤销。对实际迁移的预览或诊断入口补齐请求 token、稳定快照和独立完成状态，并复用已有 Document；任何相关编辑必须立即使请求失效。无法覆盖全部修改入口时采取更保守的整工程版本失效。

P2a 不等待 P2b；字体分批期间必须拒绝发布混代际资源。P2b 单独验证管道拥塞及进程重启。P2c 不把诊断简单延迟无限久，应合并请求并在空闲或用户主动打开诊断时完成；旧结果明确标为待更新。

P2c 必须限制后台 Python CPU 任务同时运行的数量，避免 GIL/字体锁竞争令 GUI 饥饿；不要为了预览更快而同时启动全轨布局、轨道窗口、诊断和字体小样。后台完成后的信号回调也要计时：大批单元格更新、结果转换、缓存清理应分批或缩小范围，不能把卡顿从任务入口搬到结果回调。

UI 分批以实际耗时预算控制（初始可试每片 2–4ms，再按测量调整），让出事件循环后继续；新输入优先并可使旧批次取消。不使用手动 processEvents 驱动长事务，不把 singleShot(0) 当成异步计算。不要单纯把防抖从 150ms 加到更长来掩盖问题；那只会把同一次卡顿推迟。

### 数据架构的渐进收口

第 2–8 节仍是设计契约。遇到需要改造的入口，就将该入口收口到 Document 及统一版本体系；不为纯 UI 判重强制重写全工程模型。必须坚持唯一权威数据，不能为“快速交付”新增长期双写状态。

尚未受版本/快照保护的路径不得扩大异步范围。局部渲染留到 P5；P1–P4 始终保留完整布局能力。每次发布承诺具体体验改善，不以“架构重构完成”作为用户收益。

### 各批次的体验验收

使用同一真实工程和相同操作序列比较前后。**首要指标是每次松手后 0–3 秒的 UI 心跳最大间隔、p95/p99 延迟，以及立即点击/滚动/再次输入的响应时间。** 同时覆盖后台结果抵达及偏好落盘时刻；计算超过 3 秒时继续观察到完成。P1 记录同步槽耗时，P2 记录后台竞争及结果回调耗时，P3 记录滚动/缩放延迟和刷新行数，P4 记录保存顿挫与数据完整性，P5 记录布局一致性。停手到正确帧的时间单独列为次要指标，只防止无界饥饿，不作为抢占 GUI 响应性的优化目标。

测试循环采用“连续调参 → 松手立即点击其他控件/滚动 → 再次调参”，持续至少 60 秒，并覆盖缓存填满后的数分钟运行。不能只统计全程平均帧率：它会掩盖松手后的一次明显停顿。首帧更快但 GUI 延迟恶化判为不通过；首帧稍晚但 GUI 流畅、结果正确且最终可完成，可以接受。

没有可测量收益的纯重构不挤占前述体验任务；发现正确性问题时先修复或缩回优化范围，再继续交付。

## 11. 验证要求

### 正确性

使用可控制完成顺序的测试 worker，不靠随机 sleep 证明竞态安全：

1. A 计算中提交 B；在 B 防抖启动前返回 A，A 不得发布。
2. 字号→颜色、标题→布局、全量替换→颜色连续提交，影响不丢失。
3. 撤销、切工程、关闭后旧任务返回，不覆盖状态、不操作销毁控件。
4. 字体库代际改变、同路径素材替换，旧资源结果失效。
5. 修改屏幕外页面后播放进入、远距离跳转、快速往返滚动，均取得最新内容。
6. 可见列表尚未更新时复制/批量修改/保存，仍从最新模型执行。
7. 字幕跨页重叠、段首尾、Utopia、ruby、多角色、SmartHorizon、自动间奏与双布局语义下，局部与完整布局一致。
8. 管道写阻塞/sidecar 重启时 UI 可响应，补丁基线不匹配触发完整配置。
9. 保存期间继续编辑，成功回调只确认旧 revision；导出固定快照不受后续编辑污染。
10. 多任务 busy、缓存及 pending 队列有界；取消任务不泄漏资源或污染新结果。

GPU 与 CPU 按 `layout_semantics` 的语义分别验证，不能把 CPU 画面当作绝对 oracle。增量对照使用同后端、同版本、同输入的完整路径，并区分几何一致与合理像素差异。

### 性能

使用真实多轨、ruby、多方案工程连续操作至少 60 秒，再做数分钟播放、滚动与切字体，覆盖缓存填满后的行为。分别记录 UI 事件延迟、同步提交耗时、停手到正确预览延迟、布局重算数量、过期任务耗时、队列及内存峰值。

初始目标可取常规提交 p95 小于 16ms、避免单次 UI 同步工作超过 50ms；这是待基线验证的工程目标，不是本方案已达到的结果。总耗时下降不能替代版本一致性验收。
